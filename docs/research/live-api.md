## Decisions recommended

1. **Base class: `from _Framework.ControlSurface import ControlSurface`** (what ableton-mcp uses). It ships in Live 12.0 and 12.3 (S3, S4), has `log_message()` → Log.txt, `show_message()`, `schedule_message()`, `song()` and `application()` as *methods*, and no device-provider/preferences machinery to trip over. `ableton.v2.control_surface.ControlSurface` (what AbletonOSC uses) is equally available; differences: `song`/`application` are *properties* there, and it has **no `log_message`** (AbletonOSC logs through Python `logging` to its own file). Do not use `ableton.v3` (it needs a `specification` object; built for hardware surfaces).
2. **Tick mechanism: AbletonOSC's self-rescheduling `schedule_message(1, self.tick)` loop**, one tick per `update_display()` call (Live calls it every `TIMER_DELAY = 0.1` s). Put a **non-blocking TCP listener** (`setblocking(False)` + `select([...], [], [], 0)`) in the tick and do *all* LOM access there (main thread). Wrap the tick body in `try/except Exception` and reschedule in `finally`; an exception that escapes kills the task and the loop never runs again (S3 `TaskGroup.do_update`). If you need sub-100 ms latency, ableton-mcp's pattern (daemon socket threads + `queue.Queue` + `schedule_message(0, fn)` to marshal onto the main thread) works in practice, but `TaskGroup.add` has no lock and AbletonOSC reports threads "beachball" Live — treat it as optional, not the baseline.
3. **Note API (Live 11+): `get_notes_extended(from_pitch, pitch_span, from_time, time_span)` → `Live.Clip.MidiNoteVector` of `Live.Clip.MidiNote`; `add_new_notes(iterable_of_Live.Clip.MidiNoteSpecification(pitch=, start_time=, duration=, velocity=, mute=, probability=, velocity_deviation=, release_velocity=))`; edit by id via `notes = clip.get_notes_by_id(ids); note.velocity = …; clip.apply_note_modifications(notes)`; delete via `remove_notes_extended(...)` / `remove_notes_by_id(ids)`.** Never emulate "modify" with remove+add (loses per-note events — Ableton's own docstring). `get_notes`/`set_notes`/`replace_selected_notes` are still exposed in 12.x but are the deprecated tuple API.
4. **Browser loading: walk `app.browser.<root>.children` recursively to find a `BrowserItem` by `uri` (cache uri→item per root, lazily, with a depth cap), then `song.view.selected_track = track` and `app.browser.load_item(item)`.** Position within the chain is controlled by `track.view.selected_device = dev` + `track.view.device_insert_mode = Live.Track.DeviceInsertMode.selected_right` (reset to `.default` afterwards) — this is exactly what Push 2 does. To *replace* a device: `app.browser.hotswap_target = device; app.browser.load_item(item); app.browser.hotswap_target = None`. On Live 12.3+ there is also `track.insert_device("Compressor", index)` for native devices (LOM 12.3 mirror; Python call UNVERIFIED).
5. **Colors: set `color_index` (int 0–69; `None` = no color on Track/Scene); read both `color` (int `0x00RRGGBB`) and `color_index`.** Both are settable on Track, Clip and Scene (AbletonOSC exposes `set/color` and `set/color_index` for all three); setting `color` snaps to the nearest palette entry.
6. **Target API level: Live 12.1+.** Python: Live 12.0.x embeds **3.7** (S3 headers), Live 12.3 embeds **3.11** (S4 headers); community reports put the switch at 12.1 (Ableton forum p=1832300 — blocked, seen only via search summary; NI forum notes that 12.1+ needs differently compiled `.pyc`). An Aug‑2024 12.1‑beta build still decompiles as 3.7, so the exact boundary is **medium** confidence. If 12.0 support matters, avoid 3.8+ syntax (walrus, positional-only params, `dict | dict`, `match`); otherwise 3.11 is fine.

## A. ControlSurface framework

- **Base class / imports actually used on Live 12.**
  - AbletonOSC `manager.py`: `from ableton.v2.control_surface import ControlSurface`, `from _Framework.EncoderElement import EncoderElement`, `import Live`; handlers: `from ableton.v2.control_surface.component import Component` (S1 manager.py, handler.py). AbletonOSC README: "AbletonOSC requires Ableton Live 11 or above." → **high**.
  - ableton-mcp: `from _Framework.ControlSurface import ControlSurface` (S2 line 4) → **high**.
  - `_Framework` still ships in Live 12: S3 header `Embedded file name: output/Live/mac_universal_64_static/Release/python-bundle/MIDI Remote Scripts/_Framework/ControlSurface.py`, compiled 2024‑03‑09 (12.0); S4 same path, `Python bytecode version base 3.11 (3495)`, compiled 2025‑12‑15 (12.3) → **high**.
  - v2 vs `_Framework` gotcha: `_Framework.ControlSurface.song()` / `.application()` are methods (`def song(self): return self._c_instance.song()`); `ableton.v2 SimpleControlSurface.song` / `.application` and `Component.song` are `@property` (S3 v2 control_surface.py lines 103‑109; component.py lines 79‑81). AbletonOSC code therefore writes `self.song.tracks`, ableton-mcp writes `self.song()` → **high**.
- **Entry point.** `__init__.py` must define `def create_instance(c_instance): return Manager(c_instance)` (S1 `__init__.py`; S2 line 56‑58 identical pattern) → **high**. The class constructor must call `ControlSurface.__init__(self, c_instance)` first (both sources).
- **`schedule_message(delay_in_ticks, callback, parameter=None)`** — original source (Live 10.1 `_Framework/ControlSurface.py`, https://raw.githubusercontent.com/gluon/AbletonLive10.1_MIDIRemoteScripts/master/_Framework/ControlSurface.py lines 429‑449; the Live 12.0 and 12.3 decompiles are byte-for-byte the same logic minus the asserts, identical in `ableton/v2`):
  ```python
  def schedule_message(self, delay_in_ticks, callback, parameter = None):
      u""" Schedule a callback to be called after a specified time """
      assert delay_in_ticks > 0          # stripped from the shipped Live 11/12 bytecode (0 asserts in 12.x decompiles vs 47 in 10.1)
      assert callable(callback)
      if not self._is_sending_scheduled_messages:
          delay_in_ticks -= 1
      message_reference = [None]

      def message(delta):
          if parameter:
              callback(parameter)
          else:
              callback()
          self._remaining_scheduled_messages.remove(message_reference)

      message_reference[0] = message
      self._remaining_scheduled_messages.append(message_reference)
      if delay_in_ticks:
          self._task_group.add(Task.sequence(Task.delay(delay_in_ticks), message))
      else:
          self._task_group.add(message)
  ```
  Facts that follow (S3, **high**):
  - A "tick" is one call of `update_display()`, which does `self._task_group.update(Defaults.TIMER_DELAY)`; `_Framework/Defaults.py`: `TIMER_DELAY = 0.1`, `MOMENTARY_DELAY = 0.3`, `MOMENTARY_DELAY_TICKS = int(MOMENTARY_DELAY / TIMER_DELAY)`. So **1 tick ≈ 100 ms**. AbletonOSC comment: `"""Called once per 100ms "tick"."""`.
  - `Task.delay(n)` is `DelayTask`, whose `do_update` does `self.remaining -= 1` per update (tick-counted, not time-based).
  - **Delay 0 works on Live 11/12** (the `assert delay_in_ticks > 0` of the original source is compiled out of the shipped bytecode): the callback is added directly to the task group and runs on the next `update_display`. Both AbletonOSC (`self.schedule_message(0, self.tick)` in `__init__`) and ableton-mcp (`self.schedule_message(0, main_thread_task)` from socket threads) rely on it. On Live ≤10 (non-optimised Python 2 bytecode) it raised `AssertionError` — that is where ableton-mcp's `except AssertionError` comes from. Using `1` instead costs nothing (from outside `update_display` it is decremented to 0 anyway) and is safe on every version.
  - Off-by-one: when called *outside* `update_display` (from `__init__`, a listener callback, or another thread) `delay_in_ticks` is decremented first, so `schedule_message(1, f)` from `__init__` fires on the very next tick, and `schedule_message(0, f)` becomes `delay(-1)` which also completes on the first update.
  - `parameter` is tested with `if parameter:` — a falsy parameter (0, "", None) is dropped and `callback()` is called with no args. Use a closure instead.
  - **Thread safety:** `TaskGroup.add` just does `self._tasks.append(task)` with no lock. ableton-mcp calls it from its socket threads and wraps it in `try: ... except AssertionError: main_thread_task()`; on Live 11/12 that except never fires (asserts stripped), so it is a legacy no-op safety net — and note its fallback would run the LOM mutation *on the socket thread*, which is exactly what you want to avoid. AbletonOSC's stance (manager.py): "Live's embedded Python implementation does not appear to support threading, and beachballs when a thread is started. Instead, this approach allows long-running processes such as the OSC server to perform operations." ableton-mcp nonetheless ships daemon threads and is widely used → conflicting evidence; **medium** that threads are workable, **high** that the single-threaded tick is safe.
  - **Exceptions in a scheduled callback:** `TaskGroup.do_update` catches `Exception`, calls `task.kill()`, logs `"Error when executing task"` plus `traceback.print_exc()` (goes to Log.txt). The ControlSurface survives, but a self-rescheduling tick that raises *before* rescheduling stops forever. AbletonOSC guards this by having `OSCServer.process()` catch everything internally:
    ```python
    def tick(self):
        logger.debug("Tick...")
        self.osc_server.process()
        self.schedule_message(1, self.tick)
    ```
- **`Live.Base.Timer`** — exists (S6 class `Live.Base.Timer`: "A timer that will trigger a callback after a certain inverval. The timer can be repeated and will trigger the callback every interval. Errors in the callback will stop the timer."; methods `start()`, `stop()`, `restart()`, property `running`). Constructor kwargs from Ableton's own usage (S3 `Push2/notification_component.py`, `ableton/v3/control_surface/display/state.py`): `Live.Base.Timer(callback=fn, interval=int_milliseconds, repeat=False)` then `.start()`, or `Live.Base.Timer(callback=fn, interval=int(delay*1000), start=True)`. Units: **milliseconds** (int). Keep a reference to the Timer object (Push stores it on `self`) → **high** for existence/signature, **medium** that the callback runs on the main thread (implied by Live's use; not documented).
- **`log_message(*message)`** (`_Framework` only): formats `"(%s) %s" % (self.__class__.__name__, " ".join(map(str, message)))`, logs via Python `logging` and calls `self._c_instance.log_message(message)` → appears in Log.txt. v2 `SimpleControlSurface` has no `log_message`; use `logging.getLogger(...)` (AbletonOSC adds its own `FileHandler` to `<script dir>/logs/abletonosc.log`) or `self._c_instance.log_message(str)` → **high**.
- **`show_message(message)`**: `self._c_instance.show_message(message)` — shows text in Live's status bar (both sources use it for "Listening on port …") → **high**.
- **`disconnect()`**: called when Live closes or the surface is deselected. Override to close sockets/remove listeners then call `super().disconnect()` (AbletonOSC) / `ControlSurface.disconnect(self)` (ableton-mcp). Base implementation disconnects components/controls and clears `_task_group` (S3) → **high**.
- **`refresh_state()`** = `self.update()` (re-sends control state); **`update_display()`** = runs the task group one tick (this *is* the tick source). Do not override `update_display` without calling super, or `schedule_message` stops working → **high**.
- **Getting the Song:** `self.song()` (`_Framework`, = `self._c_instance.song()`), `self.song` (v2 property), or `Live.Application.get_application().get_document()` (S6: "Returns the current Live Set."). ableton-mcp caches `self._song = self.song()` in `__init__` and uses it from socket threads → **high**. `self.application()` / `Live.Application.get_application()` for the Application.
- **Log.txt on macOS:** `~/Library/Preferences/Ableton/Live x.x.x/Log.txt` (e.g. `Live 12.3.5`), Windows `%APPDATA%\Ableton\Live x.x.x\Preferences\Log.txt`. Evidence: Ableton KB article 209071629 (blocked; path quoted in search summary as `Macintosh HD/Users/[Username]/Library/Preferences/Ableton/Live x.x.x/Log.txt`), corroborated by several remote-script READMEs (e.g. https://github.com/Ziforge/ableton-liveapi-tools CONTRIBUTING.md: "macOS: `~/Library/Preferences/Ableton/Live <version>/Log.txt`"). Python tracebacks from scripts land there → **high**.
- **User Remote Scripts folder:** macOS `~/Music/Ableton/User Library/Remote Scripts/<Name>/__init__.py`; Windows `Documents\Ableton\User Library\Remote Scripts\<Name>\`. AbletonOSC README: "Rename the extracted folder to `AbletonOSC`"; ableton-mcp README: "`~/Music/Ableton/User Library/Remote Scripts/AbletonMCP/`", "the location Live (10.1.13+) scans for third-party control surface scripts", "If you've moved your User Library, use its actual location (Preferences → Library → Location of User Library)". The **folder name is the name shown in Preferences → Link/Tempo/MIDI → Control Surface**; the class name is irrelevant, only `create_instance` in `__init__.py` matters → **high**. The legacy `Preferences/User Remote Scripts` folder is for instant-mapping configs, not Python (ableton-mcp README).
- **`.py` vs `.pyc`; reloading:** Live imports `.py` sources directly (AbletonOSC and ableton-mcp ship only `.py`); Live writes `__pycache__/*.cpython-311.pyc` (12.3) / `cpython-37` (12.0). A stale root-level `__init__.pyc` beside `__init__.py` shadows the source (community report, djaboxx/iron-static) → delete `.pyc`/`__pycache__` after edits (**medium**). **Code changes require restarting Live** (AbletonOSC README: "Restart Live"; ableton-mcp README: "restart Ableton (or re-select the AbletonMCP control surface) so Live loads it"). Deselect/reselect re-runs `create_instance` but Python keeps `sys.modules`, so AbletonOSC implements a dev-only `/live/api/reload` that calls `importlib.reload()` on each submodule then rebuilds handlers → **medium-high**.

- Supported on: Song (tempo, is_playing, signature_*, loop*, metronome, record_mode, session_record, current_song_time, tracks, visible_tracks, return_tracks, scenes, cue_points, root_note, scale_name, scale_intervals, appointed_device, …), Song.View (selected_track, selected_scene, detail_clip, selected_parameter), Track (name, color, color_index, mute, solo, arm, devices, clip_slots, playing_slot_index, fired_slot_index, arrangement_clips, output_meter_*…), ClipSlot (has_clip, is_triggered, playing_status, has_stop_button), Clip (name, color, notes, playing_status, playing_position, loop_start/end, looping, muted, is_recording…), Device (name, parameters, is_active), DeviceParameter (`add_value_listener`, `automation_state`, `state`), Browser (hotswap_target, filter_type, full_refresh), Application (control_surfaces, open_dialog_count). - Pitfalls (both sources): remove every listener in `disconnect()` and when the target disappears; removing a listener from a deleted object raises — AbletonOSC: "This exception may be thrown when an observer is no longer connected -- e.g., when trying to stop listening for a clip property of a clip that has been deleted. Ignore as it is benign." Re-register per-track/clip listeners on `tracks`/`has_clip` changes (ableton-mcp `_rebind_track_listeners`, `_bind_clip_listeners`); keep callback references (identity is needed for removal); `add_current_song_time_listener` fires at high rate (AbletonOSC throttles to beat changes); listener callbacks run on Live's main thread, so enqueue rather than do socket I/O inside them (ableton-mcp uses a lock-protected list capped at 500 events). Notes-changed: `clip.add_notes_listener(cb)` (ableton-mcp). → **high**.

## J. Threading and performance pitfalls

- **Main-thread rule.** All LOM reads/writes should happen on Live's thread (the tick / `update_display`, listener callbacks, `Live.Base.Timer`). ableton-mcp performs *reads* directly on socket threads and only marshals *writes* ("Commands that modify Live's state should be scheduled on the main thread … This enforces that Live's LOM mutations happen on the scheduler thread"); AbletonOSC does everything in the tick. Follow AbletonOSC → **high**.
- **Non-blocking I/O in the tick.** AbletonOSC: `self._socket.setblocking(0)`; `process()` loops `recvfrom(65536)` until `socket.error` with `errno.EAGAIN/EWOULDBLOCK` (benign), treats `ECONNRESET` as benign on Windows, logs everything else, and catches `Exception` around the whole loop so the tick never dies. For TCP: non-blocking `accept()` + per-client `recv()` with `select(..., 0)`; expect `BlockingIOError`.
- **Never block the tick.** Anything over a few ms stalls Live's UI/audio thread scheduling. ableton-mcp caps request bodies at 16 MB (`MAX_REQUEST_BYTES`), limits browser serialisation (depth 1, 64 children), caps rack recursion (`_MAX_CHAIN_DEPTH = 4`), caps the passive-event queue (500) and uses 10 s / 60 s (`create_audio_clip`) timeouts waiting for main-thread results. Chunk large note writes / snapshots across ticks if needed.
- **Batch note writes:** one `add_new_notes(tuple_of_specs)` call per clip, not one call per note (both sources build the full tuple first). Clear with a single `remove_notes_extended(0, 128, 0.0, length)` (ableton-mcp `_clear_notes_from_clip`).
- **Framing / errors:** ableton-mcp accumulates raw bytes and only `json.loads` when a complete object parses ("A multi-byte UTF-8 character … can straddle two recv() boundaries"); on any handler error it replies `{"status":"error","message":…}` and closes the connection to resynchronise. Every handler is wrapped in `try/except Exception` + `self.log_message(traceback.format_exc())`.
- **Exceptions inside scheduled callbacks** are swallowed by `TaskGroup` (task killed, traceback to Log.txt) — so a self-rescheduling tick must reschedule in `finally`. AbletonOSC's `/live/api/reload` clears and re-registers everything because stale listeners "continue to report after a reload".
- **Properties that raise:** `track.arm` on master/return/group (`RuntimeError`), `track.fold_state` on non-group tracks, `rack.chains` when `can_have_chains` is False, `param.value_items` when not quantized, `param.default_value` when quantized, `clip.automation_envelope` returns None on arrangement clips; `Live.Base.LimitationError` when exceeding track/scene limits (Push catches it). Guard every getter (`AbletonOSCHandler._get_property` catches `RuntimeError` → None).
- **`show_view` from `__init__`** raises RuntimeError ("Live's initialization scope") — defer UI calls to the first tick.
- **Startup ordering:** bind the socket in `__init__` but tolerate `OSError` (port in use) and `show_message` it (AbletonOSC). `Live.Application.get_application().view.show_view` and browser access are fine after init.
- **No busy threads:** if you do spawn threads (ableton-mcp), make them daemon, poll `self.running`, use `settimeout(1.0)` on `accept()`, and never touch LOM objects from them except via `schedule_message` + `queue.Queue`.
